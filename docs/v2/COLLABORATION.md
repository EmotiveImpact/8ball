# Revocable collaboration and reviewed client projections

Engineering components for **B03-03**, not an enabled secure portal. 8BALL stays
the fixer; ENDSTATE remains the underlying reusable engine. No external sharing,
send, action approval, effect application or independent professional review is
implemented by making a grant or reviewing a projection. The original local `/`
and `/v2/` apps and alpha import/audit formats are unchanged.

## Implemented lifecycle

- `Collaboration.create_grant`: immutable request ID, issuer/subject recipient,
  exact matter or object, expert/client purpose, aware start/expiry and rationale.
  Only exact retries are idempotent; reused IDs cannot change scope or revive a
  revoked grant. Expert matter grants still read one explicitly named object at
  a time; they do not expose whole-case exports or listings.
- `revoke_grant`: terminal, durable, audited; current matter administrators may
  revoke even if an object has since been removed. Future reads deny after
  revocation. Bytes already returned cannot be recalled.
- `Projections.draft`: separately curated bounded content, exact recipient,
  case/object/source revision binding and immutable digest. Client grants must
  name this exact object/projection/recipient. No client visibility follows from
  a draft or grant alone.
- `inspect`: internal-only review view with exact content, digest and stale-case
  flag. Its stale flag compares revision bindings, not source scan/retention
  readiness; the transaction gate still denies review/read on lifecycle failures.
- `review`: exact digest and exact grant, meaningful rationale and a current
  internal reviewer distinct from author **and** recipient. Review is local
  disclosure review, not factual attestation, action approval or external send.
- `withdraw`: terminal local withdrawal; no external cancellation claim. Changed
  content or revisions require a new projection ID and separate review. A
  replacement grant cannot silently repair a revoked reviewed grant.
- `client_read`: current client role, exact recipient, active exact grant,
  unchanged grant digest, current reviewer authority, matching revisions and
  current source lifecycle are all required. Its only response fields are
  `id`, `content`, `reviewed_at`, `action_permission=false`, `external_send=false`.
  No internal object, source metadata/handle, binding, authorship, reviewer,
  review rationale or grant ID is returned. Curated text is reviewed, not an
  automatic redaction engine; an independent reviewer must assess its content.

Content contains title, summary and typed statements (`unknown`, `unverified`,
`source_supported`, `disputed`). Unknown remains unknown. No data is generated by
a model, and a `source_supported` label itself does not verify a fact.

## Mandatory host adapters: no fallback

Construct `Collaboration(path, policy=..., cases=..., sources=..., clock=...)`, then
`Projections(collaboration)`. No adapter defaults to permission. Passing `None`
fails; importing or constructing services does not migrate/start anything.
`initialize()` explicitly creates **only** `collaboration_grants`,
`collaboration_projections` and `collaboration_audit`. Integration must approve
that lane-local schema against its shared migration/backup process, and invoke
it only on the intended engineering database, never discover an operator store.

All operations use `BEGIN IMMEDIATE` on `path`. The following adapters must use
that same active connection and must not commit, roll back, await, perform remote
I/O, or open another database as a substitute:

1. `CurrentPolicy.require(db, identity, binding, capability) -> None`: deny unless
   server-owned current identity/membership and exact tenant/matter/object grants
   permit the named capability. Revalidate the requesting session/token in the
   authenticated host, and durable subject/reviewer authority on every service
   call and final gate. Use `AccessRegistry.require(identity, case_id, operations,
   object_ids=..., db=db)` from the identity lane as a transaction policy
   primitive, **plus explicit server-owned role/capability distinctions**.
   Generic READ/WRITE alone must not mean disclosure review, role management or
   client access. A collaboration grant supplements current host policy; it is
   not a new bearer or a grant of broad agency access.
2. `CaseObjects.binding(db, case_id, object_id|None) -> Binding`: server-owned
   organisation/matter/object binding, current case/object revision and exact
   referenced immutable source versions/hashes/vault revisions. IDs must never
   silently be reassigned across tenants/objects. Empty sources are permitted
   for genuinely manual source-free records only; do not omit unavailable or
   inaccessible references to evade lifecycle checks. `expert_view(db,binding)`
   returns exactly the authorized object, never the surrounding case by default.
3. `SourceLifecycle.require_current(db,binding,identity=...)`: fail closed for
   every referenced source. `VaultSources(vault)` is the supplied concrete
   wrapper for the **agreed** vault transaction seam:

   ```python
   vault.require_source(
       db, identity=identity, case_id=binding.case_id,
       object_id=source.object_id, expected_revision=source.vault_revision,
       expected_sha256=source.sha256,
   )
   ```

   The wrapper checks schema 1 and exact source version/hash, case, organisation
   and matter, then discards the handle. Vault requires the active transaction
   to point to its exact database and checks current source-reference READ,
   clean release/scan, vault revision, integrity and policy/retention state.
   Standalone `metadata`/`source_handle` calls are **not** commit authorization.
   Source checks execute before and after mutation/audit, in the same
   transaction; source-gate audit rolls back with failed mutation. Missing vault
   keys, policy, scan, lifecycle or transaction adapters must deny, never treat
   upload metadata as reviewed evidence.

Client reads use the stored **still-current reviewer** as source-gate identity,
while separately checking the current client projection capability and exact
grant. This checks continued source readiness without granting a client internal
source READ or exposing any source handle. If reviewer source access is revoked,
the client read fails. Source bytes require the vault's separate READ+DOWNLOAD
permission; nothing here returns them to clients. This wrapper is contract-tested
with controlled gates; actual identity/vault/case integration requires its own
negative and native tests.

### Capabilities and route mapping

All paths below are relative to the existing authenticated agency router, e.g.
`/api/v2`, never the local operator bearer router. Prefix
`C=/cases/{case_id}/collaboration`,
`P=C/objects/{object_id}/projections/{projection_id}`.

| Method and path | Mandatory service capability | Host operation floor |
| --- | --- | --- |
| GET C/grants | collaboration.manage, whole matter | READ plus grant-management role |
| POST C/grants | collaboration.manage, requested scope | WRITE plus grant-management role |
| POST C/grants/{grant_id}/revoke | collaboration.manage, whole matter | WRITE plus grant-management role |
| GET C/objects/{object_id}/expert/{grant_id} | collaboration.expert + exact active grant | READ exact object |
| POST C/objects/{object_id}/projections | projection.draft | WRITE exact object |
| GET P/review | projection.inspect | READ exact object, internal role |
| POST P/review | projection.review | WRITE exact object, independent disclosure-review role |
| POST P/withdraw | projection.withdraw | WRITE exact object, internal withdrawal role |
| GET P | projection.client + reviewed exact grant/recipient | Explicit projection-only role; never whole-case READ fallback |

`register_collaboration_routes(router, collaboration, projections)` requires a
verified `Identity` in `request.state.agency_identity`; missing state (including
an otherwise valid local operator bearer) returns 401. Service policy remains
mandatory even with that state. Unknown paths must deny. The integrator must add
exact method/path mappings in `AgencyAccess`, not a blanket collaboration prefix
permit, and preserve object-only grants not granting case listings/search/export.
Projection-only clients need an explicitly isolated mapping/policy, not a generic
WRITE/READ alias that exposes internal routes.

Success uses `Cache-Control: no-store, private` and `Pragma: no-cache`; mapped
service errors use no-store. Host middleware must cover validation/unhandled
errors with the same no-store policy and must keep the existing
`BoundedRequestBody` limit (256 KiB), including streamed bodies. Error mappings:
401 missing identity; 403 authority denial; 404 missing exact record; 409 stale,
corrupt or conflicting state; 422 invalid typed content. No source or tenant
metadata belongs in errors. Expert/client routes collapse missing, stale and
denied service states to the same 403 response to avoid identifier enumeration;
internal routes preserve 404/409 for authorized operators. The projection
service checks current policy before loading internal records. The host must
preserve uniform denial in its own authentication and route/object adapters.

## Isolated browser mounts

`web/v2/collaboration-view.js` exports:

- `mountCollaboration(root,{api,caseId,objectId,binding})`: internal grants,
  curated draft, exact digest inspection/review, revoke/withdraw. `binding` is a
  server-supplied current `Binding`; reload host context after revision changes.
- `mountClientProjection(root,{api,caseId,objectId,projectionId})`: separate
  read-only allowlisted projection view. Refresh clears old content before a
  read; future revocation denies, but an already delivered response is not
  recalled. No browser-push or offline recall claim.

Both return cleanup functions; host navigation must call them. Inject an
authenticated `api(relativePath, options)` that returns parsed JSON and throws
on non-2xx. No bearer/session storage is added here. Add
`collaboration-view.css` via existing CSP-safe assets; do not add inline handlers,
inline scripts, loosen CSP, or place these mounts on a default client internal
case route. Unknown mutation outcomes lock further mutations until refresh;
there are no automatic retries, sends or provider calls. Exact idempotency IDs
remain operator-visible. UI syntax is checked; the new mounts have not received
a native browser journey, usability or assistive-technology review.

## Verification and acceptance boundary

See the lane receipt in `docs/delivery/lane-reports/collaboration.md` for exact
results and retained failures. Controlled SQLite/FastAPI tests exercise real
service transactions but not deployed OIDC, actual vault encryption, concrete
case adapters or tenant isolation infrastructure. No signed URLs, bespoke crypto,
external calls, production records, model downloads or implicit sends are used.
No B03-03 global acceptance follows until B03-01/B03-02 dependencies, central
wiring, integrated isolation/native checks and any independent production gates
are actually satisfied. Canonical task/status/changelog/emergence integration
remains serial and integrator-owned.
