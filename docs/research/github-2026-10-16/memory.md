# Temporal memory assessment for ENDSTATE / 8BALL

Source-only review, 2026-10-16. No packages installed, services started, inference requested, or application files modified. Repository documentation is vendor-maintained evidence of intended behavior; implementation details below were checked against pinned source. This is research for a possible future integration, not a change to V0.2 acceptance or permission to send case data to another provider.

## Recommendation in plain language

Keep ENDSTATE/8BALL's SQLite case and audit records authoritative. If later experiments demonstrate a retrieval problem, Graphiti is the most directly relevant self-managed temporal graph candidate. Zep Cloud is the managed alternative when paying another service to operate memory is acceptable. Choose one optional retrieval provider; do not add Cloud, Graphiti and Mem0 together by default. None is necessary to complete the present V0.2 acceptance work, and none supplies independent model evaluation or human acceptance.

**Zep Cloud, simply explained:** it is an external memory service for applications using AI. The application sends permitted messages, documents or events; Zep stores them, organizes entities and relationships, tracks time and returns relevant earlier context. The application still needs its own reasoning/model provider and application logic. It is neither a social simulator nor a decision authority. Hosted Zep handles its service and storage operation; Graphiti makes the developer operate the surrounding system.

The public `getzep/zep` repository explicitly says it is **not the product or service**; it contains examples, integrations and tools for the hosted product. Its old Community Edition is unsupported. Cloning that repository is not obtaining a supported self-hostable Zep Cloud server. [Zep repository statement](https://github.com/getzep/zep/blob/3997767fccf83bbea7b54ad5f73554f2e5bcd54e/README.md#L17), [unsupported CE](https://github.com/getzep/zep/blob/3997767fccf83bbea7b54ad5f73554f2e5bcd54e/README.md#L66).

## What Graphiti really needs and calls

Graphiti is an open-source temporal knowledge graph framework. Its library takes episodes, extracts/resolves entities and relations and stores a graph with temporal fields and episode references. It offers prescribed entity/edge types and search recipes. It does not supply the host application's user management, review workflow, policy engine or authoritative case ledger. Zep's own comparison describes built-in users/threads/message storage and managed operations as Cloud features; the current Cloud backend is a proprietary Context Graph Engine, rather than a promise that Cloud is simply Graphiti plus Neo4j. [Comparison and architecture](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/README.md#L83).

Actual requirements and execution paths:

- Python 3.10+ and a supported graph backend. The README lists Neo4j 5.26, FalkorDB 1.1.2, or Amazon Neptune plus OpenSearch; Kuzu is explicitly deprecated. The library can accept a custom graph driver. The optional embedded FalkorDB extra requires Python 3.12+. This is an additional persistence/operations choice, not reuse of the existing application SQLite database. [Requirements](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/README.md#L154), [embedded extra](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/README.md#L190).
- The default constructor creates `Neo4jDriver`, `OpenAIClient`, `OpenAIEmbedder` and `OpenAIRerankerClient` unless alternatives are supplied. An LLM client alone does not replace the embedder or reranker. [Defaults](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/graphiti.py#L328).
- Ingestion is model work, not just a database insert. `add_episode` retrieves earlier context, creates an episode and invokes entity extraction/resolution and relation processing. The default embedder sends content to `embeddings.create`. A deployment using defaults therefore sends approved source content to OpenAI in addition to storing it in the chosen database. [Ingestion path](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/graphiti.py#L1432), [embedding API calls](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/embedder/openai.py#L40).
- Semantic search requires query embeddings. Some search recipes combine BM25 and cosine similarity with reciprocal rank fusion; those do not inherently require an LLM reranker. If the OpenAI cross-encoder recipe is selected, its reranker makes a chat-completion request per candidate passage. Do not describe all retrieval as model-free, or all retrieval as necessarily making a chat call. [RRF recipe](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/search/search_config_recipes.py#L33), [reranker calls](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/cross_encoder/openai_reranker_client.py#L85).
- Alternatives can be configured, including local-compatible endpoints, but an entirely local arrangement needs compatible extraction, embedding and any reranking providers plus their runtimes/weights. The project's own warning says smaller/non-structured-output models can produce schema failures. Local operation, quality and hardware suitability were not tested here. [Provider warning](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/README.md#L163).
- Concurrency and per-call token configuration exist. They are not a case-wide or monetary budget. The README defaults the semaphore to 10; ingestion can involve several calls, retries and embeddings. Any integration must meter actual calls/tokens, bound episode size, candidate count and retries, reserve a total run budget, support cancellation, and record partial failures before advertising a spend cap. [Concurrency](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/README.md#L255), [LLM configuration](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/llm_client/config.py#L19).

Zep Cloud's SDK instead calls `https://api.getzep.com/api/v2` by default. Hosted service extraction/embedding infrastructure is operated by Zep; this source review cannot establish its exact internal models, subprocessors, data residency, backup purge timeline or contract terms. The host application's reasoning/simulation calls remain separate. Do not assume an extra OpenAI key is required solely for using every Cloud API, or that the service has no model processing because the user only supplies a Zep key. [SDK endpoint](https://github.com/getzep/zep-python/blob/ec41ccdde6fe92dc0de378c7bfb0c2483af324ce/src/zep_cloud/environment.py#L6).

## Time, provenance and deletion are useful but need an adapter contract

Graphiti stores raw episode content by default and records `created_at` separately from the supplied episode reference time. Its `EntityEdge` includes episode references, `valid_at`, `invalid_at`, `expired_at` and reference time. These are valuable for explaining retrieval and changes over time. They are extracted/interpreted fields, not independent proof that a claim is true. In particular, the edge schema says a future promise uses the episode reference time rather than the promised future occurrence date. Do not map these fields directly onto ENDSTATE deadlines or validated event dates. [Episode fields](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/nodes.py#L318), [edge fields](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/edges.py#L263).

Episode lineage is not the application's exact Unicode source span and content hash. Retain the original document ID/hash, span offsets/hash and current retraction/review state in SQLite, and include stable references in index metadata. Search scores also are not calibrated truth or outcome probabilities: the current Zep SDK explicitly calls relevance an experimental rank-aligned score. [Cloud relevance field](https://github.com/getzep/zep-python/blob/ec41ccdde6fe92dc0de378c7bfb0c2483af324ce/src/zep_cloud/types/entity_edge.py#L53).

Deletion requires particularly careful acceptance tests:

- Graphiti's library `remove_episode` selectively deletes derived edges whose first listed episode is the deleted episode, removes entities only mentioned in that episode, then deletes the episode. This is not a general recomputation of all derived material. Because an edge may list several episodes, the first-episode rule also means preserving independently supported facts cannot be assumed. [Exact implementation](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/graphiti.py#L2164).
- Its companion server's episode-delete path calls `episode.delete` directly, rather than the library's `remove_episode`; the two cleanup paths differ. Do not rely on the existence of an HTTP DELETE route as proof of complete cascade/retraction semantics. [Server path](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/server/graph_service/zep_graphiti.py#L73).
- Zep's public SDK exposes episode deletion and graph deletion; user graph deletion uses a separate user API. SDK surface alone cannot prove cascade behavior, retained logs/backups or contract-level deletion guarantees. [Episode API](https://github.com/getzep/zep-python/blob/ec41ccdde6fe92dc0de378c7bfb0c2483af324ce/src/zep_cloud/graph/episode/client.py#L296), [graph API](https://github.com/getzep/zep-python/blob/ec41ccdde6fe92dc0de378c7bfb0c2483af324ce/src/zep_cloud/graph/client.py#L1152).

A future adapter should first tombstone/retract canonically, prevent reuse immediately, enqueue an idempotent projection deletion/rebuild, and record completion/retry status. Case deletion, one-source retraction, shared-support facts, entity summaries, backups and provider logs are distinct acceptance cases. A stale external index must not override the local source's retracted status.

## Graphiti cannot replace MiroFish's Zep dependency by changing a URL

MiroFish explicitly hardcodes the Cloud endpoint and rejects `ZEP_API_URL`. Its current integration pins `zep-cloud==3.25.0`; the separately reviewed latest SDK is 3.30.0, so proposed replacements must respect the actually pinned contract. [Endpoint and rejection](https://github.com/666ghj/MiroFish/blob/7657031ac01184afe2cb220f5ee3545573b5e843/backend/app/utils/zep.py#L21), [client configuration](https://github.com/666ghj/MiroFish/blob/7657031ac01184afe2cb220f5ee3545573b5e843/backend/app/utils/zep.py#L65), [pinned dependency](https://github.com/666ghj/MiroFish/blob/7657031ac01184afe2cb220f5ee3545573b5e843/backend/pyproject.toml#L20).

The coupling includes graph creation, typed ontology, batched ingestion/reconciliation, processed status polling, paginated nodes/edges, graph search and simulation-activity ingestion. Graphiti's own HTTP server has a different API and does not implement the Cloud SDK protocol. [Graph creation](https://github.com/666ghj/MiroFish/blob/7657031ac01184afe2cb220f5ee3545573b5e843/backend/app/services/graph_builder.py#L218), [ontology](https://github.com/666ghj/MiroFish/blob/7657031ac01184afe2cb220f5ee3545573b5e843/backend/app/services/graph_builder.py#L313), [batch/polling paths](https://github.com/666ghj/MiroFish/blob/7657031ac01184afe2cb220f5ee3545573b5e843/backend/app/services/graph_builder.py#L407), [Graphiti server ingest API](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/server/graph_service/routers/ingest.py#L51).

Two honest integration options exist:

1. Keep MiroFish as a separate Cloud-dependent research application and import reviewed, attributed results through ENDSTATE's provider boundary. That is the smaller experiment but retains Cloud credentials, data-processing and cost dependencies.
2. Fork MiroFish to put its memory operations behind a provider interface, implement a Graphiti adapter, and validate ID mapping, ontology, batch completion/failure/idempotency, pagination, temporal search, deletion/rebuild and reporting contracts against frozen fixtures. This removes a mandatory Cloud service only after substantive implementation and validation; it adds graph database and inference operations.

MiroFish writes generated simulation activity back to its graph with `source=mirofish_simulation`, simulation ID, platform, round range and agent IDs. That is valuable provenance, but also why generated episodes must occupy a separate scenario namespace from observed evidence. Later graph retrieval must not silently turn a simulated event into an observed case fact. [Activity ingestion](https://github.com/666ghj/MiroFish/blob/7657031ac01184afe2cb220f5ee3545573b5e843/backend/app/services/zep_graph_memory_updater.py#L494).

## A bounded alternative: Mem0

Mem0 is worth retaining as a comparison for simpler conversational/preferences memory. Its OSS library defaults to an OpenAI LLM, OpenAI embeddings and Qdrant vector storage; Qdrant can use a local path without a separate server when no remote connection parameters are provided. It also maintains a separate SQLite history database. [Defaults](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/configs/base.py#L29), [LLM](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/llms/configs.py#L6), [embedder](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/embeddings/configs.py#L6), [local vector path](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/vector_stores/qdrant.py#L60).

Its `add` API defaults to an LLM extracting memories and deciding additions, updates or deletions. `infer=False` skips that extraction but still creates embeddings; with the default embedder that still involves an external model call. The `timestamp` parameter is explicitly unsupported in OSS, so it should not be described as a drop-in temporal Graphiti substitute. [Add semantics](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/memory/main.py#L760), [non-infer embeddings](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/memory/main.py#L903).

Mem0's history records old/new memory text, events and deletion state, which is useful for debugging, but does not replace the application's command/review ledger. Deleting current searchable memory does not mean that this history or backups are automatically erased. [History implementation](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/memory/storage.py#L227). It is a different design tradeoff, not another mandatory layer to stack onto a temporal graph.

## What must remain canonical in ENDSTATE's host application

The host application owns SQLite persistence; the reusable ENDSTATE engine should remain independent of a particular memory service. Preserve these records and responsibilities locally:

- Case identity, revision, current snapshot, transactional command history, idempotency and audit hashes.
- Original source text and hashes; exact excerpt offsets/hashes; source status and retraction reason; evidence lineage and human review dispositions.
- Reviewed observations, contested/unknown claims, constraints, goals, chosen course, action approvals and completion evidence. Model extraction, entity merging and edge invalidation remain proposals or retrieval signals, not automatic authority to change these.
- Model/provider request authorization, purpose, scenario/case scope, budgets, prompts, raw output or bounded failure evidence, evaluation and review disposition, subject to the application's retention policy.
- Any future external-index ID mapping, projection version/watermark, tombstones, deletion/retry receipts and rebuild status. These last integration records are a proposal, not a claim that they already exist.

This matches the existing application's revisioned case/event/proposal/source tables and transactional review. Exact source text, offsets and hashes already have stronger grounding semantics than a generated graph relation. [Current store](https://github.com/EmotiveImpact/8ball/blob/d7d36b842464d7ad0e974a59730a682f1739fccf/eightball/v2/store.py#L14), [revision guard](https://github.com/EmotiveImpact/8ball/blob/d7d36b842464d7ad0e974a59730a682f1739fccf/eightball/v2/store.py#L109), [proposal review](https://github.com/EmotiveImpact/8ball/blob/d7d36b842464d7ad0e974a59730a682f1739fccf/eightball/v2/store.py#L141), [source hash/span checks](https://github.com/EmotiveImpact/8ball/blob/d7d36b842464d7ad0e974a59730a682f1739fccf/eightball/v2/source_desk.py#L195), [canonical source retraction](https://github.com/EmotiveImpact/8ball/blob/d7d36b842464d7ad0e974a59730a682f1739fccf/eightball/v2/source_desk.py#L243).

The resulting boundary is: canonical reviewed records -> permitted, versioned memory projection -> attributed candidate context -> ordinary existing proposal/review commands. Keep observed source claims, unverified model hypotheses and hypothetical simulation outputs in separate namespaces. An index outage or rebuild should reduce retrieval convenience, not lose the case or authorize an action.

## Evidence limits and a useful later experiment

This review validates source-level integration feasibility, not runtime reliability, retrieval accuracy, deletion completeness or predictive validity. Zep ships LoCoMo/LongMemEval tooling; the inspected LoCoMo harness requires Zep and OpenAI keys and configures a response model and grader. That supports measuring conversational-memory retrieval, not independent evidence of ENDSTATE planning or real-world prediction. The shown configuration uses the same model for response and grading, so it would not satisfy the project's independent-evaluation requirement by itself. [Harness prerequisites](https://github.com/getzep/zep/blob/3997767fccf83bbea7b54ad5f73554f2e5bcd54e/benchmarks/locomo/README.md#L48), [response/grader configuration](https://github.com/getzep/zep/blob/3997767fccf83bbea7b54ad5f73554f2e5bcd54e/benchmarks/locomo/README.md#L95).

After V0.2 acceptance and explicit approval of an isolated research experiment, compare the current deterministic source retrieval baseline with one memory provider on frozen synthetic/permitted cases. Require exact citation recovery, revision/case/scenario isolation, contradictory and future-dated claims, retraction/shared-support deletion, replay/rebuild behavior, recorded model/provider usage, latency and total cost. Keep the independent human/reference labels separate from generator/reranker output. Adopt additional infrastructure only if that evidence shows a useful gain.
